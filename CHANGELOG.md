# Changelog

What changed in each version, newest first. Each version has two parts: **For players** is the release notes in plain words, and **Technical changes** is the full record. Versions are `X.Y.Z` (`installer/VERSION`); 0.1.0 to 0.6.0 are pre-releases, and the first full release will be 1.0.0. The technical part follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/). How to write an entry, with a template: `CONTRIBUTING.md`.

## [Unreleased]

### For players

**Fixed**

- **Rollback over re-psn: the two games now wait up to 2 minutes for each other.** Before, the joining game looked for the host's room only once and gave up at once if it was not there yet, and each game stopped waiting after 30 seconds. Now the joining game keeps looking until the host's room appears, and either game can start first: start both at about the same time, because each one waits 2 minutes after it has finished starting up. While it waits, the main menu's top list shows what it is doing; if the two games do not meet, it says why and what to check, with the build number both players should compare. The on-screen messages have not been seen in a game yet.
- The launcher's Online tab no longer lets you switch on re-psn or a community server while rollback is on (that made the game refuse to start any online play). It says so and keeps the tab on Off; Server and Online name can now be filled in and saved while Off is chosen, so rollback setup no longer needs re-psn switched on first.

### Technical changes

#### Fixed

- **Rollback over re-psn, rendezvous:** the joiner no longer fails on its first room list (`re-psn: no rollback room for this build` came from the first empty search, `jsp_net_repsn.h`); it reads the list again every 2 s (`kLookupEveryMs`, one request in flight) until its window ends. The window is 120 s for both roles (`kRendezvousWindowMs`, was 30 s) and covers finding the other player only; the punch keeps its own `punch_ms`. The host's room stays listed until it gives up. Both sides log `[net] re-psn: looking for a host ...` / `[net] re-psn: room open, waiting ...` every 10 s. The give-up text names what happened, the window, the 8-hex build word and what to check (`re-psn: no host with this version found within 2 minutes: start both games at about the same time (the host first is best; each waits 2 minutes after its own start-up); both need the same version (build xxxxxxxx) and the same gameplay mods (or none)`), and any rollback room of another build that was seen. The waiting state and every re-psn rendezvous failure go on the existing top-menu notice (`jsp_net_notice`, re-read through the new `jsp_net_notice_gen` whenever the text changes); the bottom message line stays empty for them, so it does not clear that shared overlay layer (a player away from the top list sees them when it comes up again). Another end before the games meet (a mods refusal during the wait) clears the waiting band (`RendezvousNotice::ended`). The first progress line comes after the connect step, so a connected game never reports "connecting". Build-word inputs and the wire protocol are unchanged: a 0.6.1 joiner also finds a 0.6.0 host's room only when the build words match, which they do not across versions. Tested: `installer/tools/net_repsn_test.sh` (fake transport: joiner first and host 60 s later, host waiting 100 s with its room listed, give-up of either side at the window with the exact texts, the 2 s list interval, the progress lines, the other-build hint, the notice store's waiting / ended / failed / met sequence; real transport against the fake wire-format server: joiner first then host, build mismatch until the window), MinGW-w64 g++ `tools/ci/port_syntax_check.py`, `tools/ci/repo_checks.py`. Not tested: a game run (no two-copy or two-PC run with this build; the notice has not been seen on screen).
- **Launcher:** `SaveOnline` (in `JStarsLauncher.cs` and `JStarsLauncher19.cs`) returns an error when re-psn or Community is chosen and `play_settings.txt` turns rollback on (`RollbackOn()`: the last `JSP_ROLLBACK=` line at column 0, trailing space/CR/LF trimmed, on when not empty and the first character is not `0`, letter case ignored; the same rule as `launcher.c` and the game for files the launcher or the game wrote, hand-edited files can still differ at the edges, e.g. a lone CR as a line break, and an inherited environment variable is not seen), so Start Game with an unsaved Online tab stops too. A file that already says `enabled=1` on disk only shows a note in `LoadOnline` (appended to a load error if there is one); the game then refuses with its own notice. The re-psn panel stays enabled while Off is chosen, and Off writes a valid server and name even when `repsn.ini` did not exist. The launcher still never writes `JSP_ROLLBACK`. `docs/ROLLBACK.md`'s setup step now says to leave the tab on Off. Tested: `installer/tools/online_option_test.py` (new source checks and a model of the parser rule), both launcher files compiled with Mono's `mcs`. Not tested: the window itself (no Windows run).

## [0.6.0] - 2026-11-20

### For players

**New**

- **Rollback status badge (optional, experimental rollback only).** Add `JSP_ROLLBACK_BADGE=1` to `play_settings.txt` and a rollback match shows one small line in the top-left corner: the connection path (direct or relay), the input delay and the length of the last rollback. The support bundle shows the same values. It has not been tried in a game yet.

**Changed**

- **New look.** The project page, the fan site and the installer pictures have a fighting-game menu style, and the setup, the launcher and the settings window have a new icon: a star with a J. The installer pictures, the new icons and the settings window header are not tried on Windows yet.
- The Discord invite on the project page is the new one.
- **Rollback over a re-psn room has run its first match on two PCs** on one home network, with no desync. It was a scripted test match, not played by hand. Start both games within about 30 seconds of each other (the host first); the rollback guide explains the two "timed out" and "no room" messages. The match ran slowly, and why is not known yet. A 0.6.0 game cannot play rollback against a 0.5.1 one: both players need the same version.
- **The support bundle hides your online details.** It replaces the server and join addresses, online names (yours and other players') and your Windows user name with placeholders in every file, and it says which netcode your settings chose and how the last two starts went. Look over the zip before you post it: an address typed only on the command line, or an IPv6 address, is not caught. Not tried on Windows yet.
- **Port Settings is on by default.** Options now has a sixth row, Port Settings, at the top of the list, without any setting, so the Online page where you choose Off, Delay or Rollback is easy to find (US version of the game only). The Netcode row was opened and switched to Rollback in a running game; saving it and playing a match from it are not tried yet.

**Fixed**

- **Build again** in the settings window rebuilds game files that were removed after a build (for example by an antivirus), instead of saying the build is done while the game still cannot start. Tested only by script so far, not on a real install.
- The fan site's tables keep their words whole, and its menu is one straight list with no second row of buttons.
- **Online menus:** sending a room invitation, opening the invitations you received or viewing a player's profile left the game on "Communicating..." for good. These screens should now back out right away, as if you had pressed back, since the PC version has no system window to show them; this has not been tried in a game yet.
- **Rollback that cannot start now says why on screen.** When rollback is asked for but cannot start (for example because the game's own online is switched on too), on the US 1.00 build the main menu shows the reason and the fix at the top of the screen for a few seconds (on the EU build only the log says why), instead of the match just not connecting. The rollback guide has a step-by-step setup for rollback over a re-psn server. Seen in one test run on the US 1.00 build with the game's own online and rollback both on: the notice showed on the main menu and came back after Options. Not tried on Windows yet.
- The version number in the main menu's lower right corner showed only the first time the main menu came up: after going into Options and back it stayed off. It now shows again each time the main menu's list is up. Seen in one test run on the US 1.00 build.
- **The game's log no longer fills up while you are online.** The game's online code no longer writes your online name, or other players' names and addresses, many times a second. The rollback lines still name the server, your online name and a typed join address, and the support bundle replaces them with placeholders. A support bundle keeps the start of the log again. Not tried in a game yet.
- **Shader warm-up cache:** for long-time players the warm-up file `pipelines.bin` stopped working after it passed 2 GB, so every start rebuilt the pipelines and the file kept growing. It now loads, is cleaned of repeats and damaged records, and stays within 16384 pipelines (about 2.3 GB); a full or unreadable cache says so in the log. When it is full it keeps the first pipelines it saw until the game's graphics code changes. The first start after the update may take longer while it cleans the file; a later version that changes the graphics code starts the cache over. Not tried in a game yet.

### Technical changes

#### Added

- **Rollback:** an opt-in status badge, `JSP_ROLLBACK_BADGE=1` (default off, read once at start): while a rollback session runs, `Rollback | <direct or relay> | delay <N>f | last <M>f` at scale 0.5 in the top-left corner above the fight HUD's top bar, on the glue's overlay layer next to its messages, rebuilt at most four times a second and redrawn only on a change (or when another user closed the layer). Path, input delay (the manifest's value) and the length of each rollback (current tick minus the rollback target, newly counted) come from the session; the game logs `[net] status badge: on|off` at start and `[net] status: path ..., delay ..., last rollback ..., largest ..., rollbacks N` every 30 s and at the end of a session. The support bundle's Netcode section reports whether the key is on and, per launch, the last status line (matched exactly, so no address or name can pass). No launcher box or Port Settings row (both launchers would need a new key; the key plus `docs/ROLLBACK.md` is enough for testers). Tested: the new host test `installer/tools/net_badge_test.sh` (text, key, refresh gate, layout, and every status line the game can write is read as written by the bundle), `installer/tools/support_bundle_test.py`, and a MinGW-w64 syntax check of `jsp_net_game.cpp`. Not tested: a game run; the badge has not been seen on screen.
- **Support bundle:** `facts.txt` has a Netcode section: the mode from the settings files, decided as the game decides it (Off, Delay over re-psn, Rollback direct or over re-psn, host or join, relay allowed or not, or the refusal and why; play_settings.txt read as the launcher reads it, including a `PS3RECOMP_SHARED_DIR` line; server, join address and online name only as set or not set) and, for the last two launches, what the `[net]` lines say (rollback started, refused and why, path, session synchronized, rollback and desync counts, key lines), read from the raw logs before the size cap cuts them and printed line by line without the server, join address or online name (a name such as "net", "host" or "relay" leaves the section's words alone); every file in the zip, and its file name, now has placeholders for the server and join addresses and online names from the settings files (also commented-out and earlier lines), the Windows login name (the game uses it as the online name when none is set), the names, server, peer address, community preset labels and unknown section names in the known online log lines and settings files (also other players' online names; LF or CRLF), and every IPv4 address except loopback and 0.0.0.0; not caught: a name or server in none of these (for example one given only on the command line, or an IPv6 address), and settings from a file given to the launcher with `--settings`; both launchers keep the previous `play_stderr.txt` as `play_stderr.prev.txt`. Tested: `installer/tools/support_bundle_test.py`; `launcher.c` and `JStarsLauncher.cs` compiled (MinGW-w64, Mono), not run on Windows.
- **Fan site, README and installer art:** a new look in the style of a fighting-game main menu, drawn by the project (no game art), around the ASCII star with the J, which is also the icon of the setup, the launcher and the settings window (shown in its header). The README has menu buttons and palette badges; the site is walked like a menu (Up/Down, Enter, Esc, a game pad or a tap) and has a no-script plain page; there is a new social preview image; one palette file (`data/theme.json`) drives all of it (`tools/site/`); the new Discord invite (https://discord.gg/D2eTEnCK62) is used everywhere. Tested: `tools/site/test_site.py` (the committed images match a fresh render) and both pages in a headless browser, light and dark, at 1280 px and phone width. Not tested: the installer images and the settings window header on Windows. (#210)
- **Rollback:** a refused or stopped rollback start is shown on screen: `jpno::resolve_env` reports a reason code (`jpno::Refusal`) for every refusal, the `: off` exits of `jsp_net_game_install` (no server or name in `repsn.ini`, a name over 16 characters, a bad join address, no UDP socket) record one too, and the Port Settings module draws `jpno::notice_text` (two ASCII lines: what is wrong and the fix, naming `repsn.ini`, `--psnr` or `PSNR_SERVER` for the both-on case from `jsp_online_source()`); each fix line names the change in `play_settings.txt` or `repsn.ini` first and Port Settings > Online only as the alternative in a band at the top of the main menu's top list for 15 s each time the list comes up, on the overlay layer it shares with the version line. ENHANCEMENT, display only, on by default; US 1.00 build only (the top-list hooks); the log lines are unchanged. Tested: `installer/tools/net_online_test.sh` (every code from `resolve_env`, every text, the visibility rule) and `tools/ci/port_syntax_check.py` (all port sources). Run: one Proton run on US 1.00 with the both-on refusal showed the band on the top list, hidden in Options and back after Circle; other refusal reasons, other submenus and the EU build were not run.
- **Toolkit:** patch 6502 lets the port serve a file the game opens read-only through a virtual view (`include/ps3emu/fs_vfile.h`, `g_ps3_fs_vfile_ops`, NULL by default): a provider claims a cellFsOpen path; the fd keeps its real host file, and Read, Lseek, Fstat and AioRead see the provider's bytes and size (the position is kept per fd under its stream lock; a read that crosses the virtual end returns the short count; Close releases the view; cellFsSdataOpen is never virtual and logs one line when a provider would have claimed its path). It is the toolkit half of the mods framework's virtual archives; nothing sets the pointer yet, so the game is unchanged. Upstream candidate. Tested: the new host test `installer/tools/fs_vfile_test.sh` (the patch's `test_fs_vfile.cpp`: open, SEEK_END, read, fstat, a read across the virtual end, close, re-open, AioRead, SdataOpen, read-write opens; and the toolkit's five other cellFs tests, unchanged with the pointer NULL; g++ and clang++) and a MinGW-w64 syntax check of `ppu_fs.cpp`. Not tested: a game run, and the cost on the read path is not measured.
- **Mods (framework core):** `installer/port/jsp/jsp_mods_core.h`, a header with no game or toolkit dependency, holds the core of the mods folder: the enable list (`mods.txt`: one id per line, line order is load order), the manifest (`mod.json`, schema 1: id, version, interfaces, overrides of CPK entries by a file with its SHA-256 or by an alias of another entry of the player's own archive, groups, `conflicts_ok`; an unknown or newer interface or any error refuses the whole mod and the others still load), the CPK TOC rewrite (only FileSize, ExtractSize and FileOffset of an overridden row change, masked tables are re-masked) and one virtual-file plan per archive (the original bytes, the rewritten TOC, then each override at a 2048-aligned offset), conflicts (the later mod wins, with a log line; a group that loses an entry is dropped whole), the class of each mod (gameplay unless every entry is under `game/logo/`, `movie/` or `sound/`) and the mod-set digest that online play will compare (SHA-256 over the applied gameplay mods in load order with each served entry's content hash; none for a cosmetic-only set; a fixed refusing value when a listed gameplay mod could not be applied). Nothing in the game uses it yet. Tested: the new host test `installer/tools/mods_overlay_test.sh` on synthetic archives the test writes itself (g++ and clang++) and a MinGW-w64 syntax check of the header. Also checked against the archive layout of a US disc (counts and offsets only; no game data in the repo or the tests). Not tested: a game run.
- **Mods (game glue and online gate):** `installer/port/jsp/jsp_mods.cpp` reads the mods folder at start, before the guest runs (`JSP_MODS_LIST` = `mods.txt`, `JSP_MODS_DIR` = the folder, `JSP_MODS=0` turns it off; with no list nothing is registered and the game is unchanged), plans each CPK archive with `jsp_mods_core.h` from the disc copy and serves the planned archives through toolkit patch 6502. Each fd reads the original bytes from its own copy (disc or hdd0) once that copy is checked to have the planned size, header, TOC and alias bytes (a differing copy is read stock, with a log line). Mod files are opened once, with other Windows programs' writers and deleters shut out while the game runs (on Windows; under Proton a native Linux program can still rewrite them), and are hashed and served through the same handle; a file reached through a symbolic link or a junction is refused. The digest's EBOOT id is the SHA-256 of the loaded ELF, and the title id comes from PARAM.SFO. The `[mods]` lines go to `play_stderr.txt`. Online: the rollback build word is `build_id()` with the set's gameplay digest folded in (`jsp_mods_glue.h` `net_build`: unchanged with no gameplay digest, else the first 32 bits of SHA-256 of the id and the digest), so peers with other gameplay mods get BuildMismatch and the re-psn room filter hides them; gameplay mods that were listed but not all applied refuse rollback; and a gameplay set turns the game's own online off for the session (`[mods] game online refused: gameplay mod set active`; `PS3_NET_ONLINE` is removed and the Online page says "gameplay mods are on"). Tested: `installer/tools/mods_overlay_test.sh` (the pure glue; given the toolkit folder, also `jsp_mods.cpp`'s POSIX file layer on files in a temporary folder: both off paths, links refused, a listed mod missing, two archives served from disc and hdd0 copies, a differing copy not served), `session_manifest_test.sh` (the same set starts a session, another set or a stock peer gets BuildMismatch, no digest keeps the id), `online_settings_test.sh` (the refusal), with g++ and clang++; the port syntax check and a partial MinGW-w64 link. Not tested: a game run, and the Windows file branch (links, share mode) beyond compiling.
- **Launcher (mods):** `jsp-launcher.exe` passes the mods folder to the game: `JSP_MODS_LIST` is the `mods.txt` next to the settings file that won, or in the install folder when no settings file was found (a proposal still to be confirmed), and `JSP_MODS_DIR` is `<install folder>\mods` when that folder exists; a value already set is kept, and `JSP_MODS=0` passes nothing. A second line in `launcher_log.txt` says `mods: N listed (<path>)` (N counts the lines that name a mod), `mods: 0 listed (<path>, not found)` or `mods: off (JSP_MODS=0)`. The launcher only passes paths; the game reads and checks the list. Tested: built with MinGW-w64 gcc; `installer/tools/launcher_settings_test.py` has five new cases (no list, the install folder's list with a BOM, comments and blanks, the list next to the AppData settings file, an AppData settings file with no list next to it, `JSP_MODS=0`) for the Windows CI job. Not tested: those cases have not been run (they need Windows), and no game was started.
- **Mods (copy check at start, Online page):** `jsp_mods_init` now checks every copy of a planned archive the game can open before the digest is published: the disc copy and `<hdd0>/game/<folder>/USRDIR/data/PS3/<archive>` for each folder (hdd0 is `PS3_HDD0_ROOT`, else the disc root, as the toolkit maps it). It logs `[mods] check <archive>: N of M copies the game can open match the plan`. A differing copy is read stock. When a gameplay mod changes that archive, the set becomes refused (`[mods] set: refused: ...`), so rollback and the game's own online are off before any socket opens. A copy first opened later that differs logs a `[mods] WARNING` line and sets `jsp_mods_copy_mismatch()`. On Windows the archive name and the path are matched without regard to case (`jsp_mods_glue.h` `archive_key`, `path_key`). A short read on a served archive logs at counts 1, 10, 100 and so on, not on every read. When gameplay mods turned the game's own online off, the game sets `JSP_MODS_ONLINE_OFF=1` instead of the rollback refusal key, and the port's Online page reads "This session: off (gameplay mods are on); turn the mods off to play online." with no "Restart to apply". Tested: `mods_overlay_test.sh` (path keys and case folding, copy paths, gameplay archives; with the toolkit folder, two hdd0 copies checked at start, a differing copy of the cosmetic archive kept as listed, a differing copy of the gameplay archive refused, a late differing copy flagged, a path in another case claimed with the Windows match), `net_online_test.sh` (the status line and the page flag) and `online_settings_test.sh`, with g++ and clang++; the port syntax check and a partial MinGW-w64 link. Not tested: the Windows file branch beyond compiling, and a game run.
- **Mods (in-place replacement, link check):** a replacement is now written over its entry's own 2048-byte slot (the stored size rounded up), so the archive keeps its size and layout; only the row's FileSize and ExtractSize change, and the rest of the slot reads as zeros. The first layout, which put every replacement behind the archive, left the boot on a black screen even with unchanged bytes: the game reacts to the archive's size or end layout. A larger replacement is refused for now, with a log line naming the entry and both sizes (a zero-size row has no slot either). Correction to the game glue entry above: each folder and file below the mods folder is now checked for a link (symbolic link, junction or Linux-style link, by reparse tag) before it is opened, and the refusal line keeps the reason. A linked mod folder is refused, but when the game runs on Linux a linked file inside a normal mod folder is still followed (its bytes must still match the manifest's SHA-256), so "a file reached through a symbolic link or a junction is refused" holds on Windows only. Tested: `mods_overlay_test.sh` with the toolkit folder (in-place cases, refusals); a game run with an identical-bytes override (boots to the title screen) and with a same-size recoloured boot logo (shown); a linked mod folder refused and a linked file followed in a game run on Linux. Not tested: a smaller or larger replacement in a game run, and the Windows link check beyond compiling.
- **Launcher (mods, environment values):** `jsp-launcher.exe` reads `JSP_MODS`, `JSP_MODS_DIR`, `JSP_MODS_LIST` and `APPDATA` into initialised buffers and treats a value longer than its buffer as set: it passes the value to the game untouched, does not count the list, and logs `mods: JSP_MODS_LIST is longer than 519 characters: not counted here (the game reads it)`. A `mods.txt` under AppData is shown as `%APPDATA%\...` in the `mods:` line, as the settings line does. Tested: built with MinGW-w64 gcc; `installer/tools/launcher_settings_test.py` has a new case (values longer than the buffers) and checks the `%APPDATA%` form. Not tested: those cases have not been run (they need Windows).
- **Rollback (mods copy mismatch after start):** the rollback pump (`jsp_net_game.cpp`) checks `jsp_mods_copy_mismatch()` before it polls the rendezvous (direct IP or re-psn) and again right before the settings handshake's Hello. When it is set, it logs `[net] rollback refused: the mod set does not run as listed (see the [mods] lines): off` (the start-up refusal's text, `jsp_mods_glue.h` `kModsNotAsListed`) and ends the session there. A session already past its Hello is not ended. A copy that differed is checked again on a later open when its size has changed (an install still being written); the refusal already made stays. Tested: `mods_overlay_test.sh` (`rollback_gate`, the flag after a late differing copy, a truncated copy served once it is complete), with g++ and clang++; the port syntax check. Not tested: the pump path in a game run.

- Installer: `assemble_payload.py --tree legacy` (and `v15`) no longer builds the earlier v0.15 tree and exits with a pointer to the git tag `legacy-v15` (issue #152); `firstrun.py` builds only the current tree and stops with an error when `tree.txt` is missing or unknown; CI no longer builds or tests the legacy tree (the `toolkit` job and the legacy patch series check are gone, the `tree` input of `installer.yml` too).

## [0.1.0] - 2026-11-11

First pre-release. J-Stars Victory VS+ for Windows: the game is built on your PC (ps3recomp, Direct3D 12) from your own copy of the disc, no game
files are included. On the Windows PC it was tested on, it boots, plays the menus and fights with sound at about 30 frames
per second, and the installer builds and starts it. It needs a 64-bit CPU with AVX2.
It is a pre-release with known problems and fewer tests than it needs:
see [issue #9](https://github.com/Tsamiuy/jsp-vs-ex/issues/9). `docs/FEATURES.md` lists each feature with how it was tested.

### For players

This is the first pre-release: it works, but it has known problems and has been tried on few PCs. You need your own copy of the game (disc image or disc folder); no game files are included. Your PC needs a 64-bit processor with AVX2.

**New**

- **The installer:** `jsp-setup.exe` (or the portable zip) builds the game on your PC from your own copy of the disc, and a launcher starts it. On the PC it was tested on, it reaches the menus and plays fights with sound at about 30 frames per second.
- **Picture:** higher resolutions, a resizable window, borderless fullscreen, and "EX" in the title logo.
- **Controls:** play with the keyboard, the keyboard and mouse, or a controller, each with its own button layout. A second player can use the keyboard or a second controller.
- **Options:** a setting for the size of the fight HUD (the bars and icons during a fight), an Exit Game entry in the Options menu, a Hide HUD row in Training Mode, and an FPS counter.
- **Online tab in the settings window:** choose Off, a re-psn server or a community server, and a Find on LAN button looks for a server on your network. Not tried on Windows yet.
- **"Unlock everything" cheat** (opt-in, on the Cheats tab): unlocks all characters and extras. It makes a backup of your save first and works for one start only.

**Changed**

- Setup checks that your game's main file (the EBOOT) is the known version 1.00 and refuses the other region's.
- Fight intros no longer show half-drawn characters, and new objects or camera turns no longer freeze the game for a moment.
- Importing a save from RPCS3 is safer: your old save is kept if the import fails.

### What you get

- A Windows installer (`jsp-setup.exe`) and a portable zip that do that build, and a launcher to start the game.
- Higher resolutions, a resizable window and borderless fullscreen, and EX in the title logo.
- Keyboard, keyboard and mouse, or controller, each with its own bindings; a second player on keyboard or a second
  controller.
- Fight HUD size, Exit Game in Options, Training Mode, a Hide HUD row in Training and an FPS counter.
- Opt-in "Unlock everything" cheat (launcher Cheats tab, `JSP_UNLOCK_ALL=1`): save backup first, one start only.
- The features page (`docs/FEATURES.md`), generated from `docs/features.tsv`.

### Changes since the first builds

- Installer and CI: the port on ps3recomp v0.19.0 (`installer/port`) is now the default tree of
  `assemble_payload.py`, `installer.yml` (new `tree` input) and `release.yml`. The switch is `--tree current` (the default) or
  `--tree legacy` (the earlier v0.15 port); the names do not change with the toolkit version. The older `v18`, `v19` and `v15`
  are still accepted.
- Setup checks the decrypted EBOOT against the known 1.00 builds and refuses the other region's. An unknown build can
  be allowed with `--allow-unknown-eboot` (installer: `/ALLOWUNKNOWNEBOOT=1`); it is unsupported.
- Portable first run: the last line points to `jsp-settings.exe` (settings, Online tab, then Start Game) and names
  `jsp-launcher.exe` only as the direct start, or as the fallback when Windows has no C# compiler and the settings window was not built.
- Installer: the settings window (`jsp-settings.exe`, built from `launcher/JStarsLauncher.cs`) now has the Online tab
  (Off / re-psn / Community server, Find on LAN); before, only the v19 launcher had it. Start Game saves unsaved
  Online edits first. The game's reader also finds `jsp-install.ini` one folder above its `game\` folder, so a portable
  install uses `<install>\shared` as the tab does. Not yet run on Windows. `online_settings_test.sh` is now tracked, so CI can run it.
- Launcher: a Find on LAN button in the Online tab looks for a re-psn server started with `-discover` on the same
  network and fills the Server field (needs a re-psn build with LAN discovery; not tested across a real network yet).
- Launcher: an Online tab edits the shared online settings files (`repsn.ini`, `community.ini`): off, re-psn or a
  community server preset, one method at a time, written atomically; the launcher sets no online environment variable.
- Game: reads `repsn.ini` and `community.ini` at startup and sets the runtime's online variables from them (re-psn
  server and name, peer port; both methods on is refused, a community preset keeps the game offline, `--psnr`,
  `--username` and environment variables win), logging on `[online]` lines; host test in CI.
- D3D12: a vertex program seen for the first time is compiled on worker threads instead of the drawing thread, so
  new objects and camera turns no longer freeze the game for a moment (toolkit patch 2070, `VS_ASYNC=0` turns it off).
- D3D12: every pipeline a run builds is noted in `pipelines.bin` and the next start builds them all at boot, so the fight
  intros no longer show half-drawn characters while pipelines build (toolkit patch 2068, `PSO_WARMUP=0` turns it off).
- D3D12: the GPU wait only gives up on a removed device, and the deferred-release table grows instead of freeing its
  oldest entry early (toolkit patch 2066).
- RPCS3 save import stages incoming files before replacing progress, restores the old files after an I/O error,
  and refuses linked destinations that could overwrite files outside the selected save.
